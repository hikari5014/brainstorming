### 🔨 v4 要新做（文件的增量）
1. **面對面上下分區佈局**（核心）：上半 180° 旋轉面向對方、下半面向自己，
   各自有語言標籤＋狀態、大字譯文、小字原文參考（標籤用讀者語言）、按住說話鈕
2. **通話隱喻**：主畫面「開始對話」大按鈕（按下才開麥克風＋建線）、
   中控列結束通話鈕、結束後進入逐字稿檢視
3. **中間控制列**（不旋轉）：逐字稿入口 ｜ 語言對（中文 ⇄ English，含交換）｜ 結束通話；
   下方固定高度「翻譯中」跳動點區（固定高度避免版面跳動）
4. **單向聆聽模式**：只啟用 foreign→zh 一條連線、全螢幕正向單區、
   點按開始/停止聆聽（演講導覽情境不適合長按）、預設字幕為主
5. **波形收音回饋**：按住時該側按鈕旁 RMS 驅動的等化器動畫（「系統有在聽」）
6. **逐字稿留存**：IndexedDB 儲存每回合（時間、方向、原文、譯文），
   結束通話後可檢視/複製/分享（navigator.share）/匯出 .txt/清除
7. **視覺語言刷新**：扁平、大量留白、單一強調色（互動/進行中元件統一）、
   outline 圖示、44pt 觸控目標、aria-label、rem 動態字級

### ⚖️ 不採用的建議（與理由）
- **Next.js + LiveKit + Supabase + Vercel**：不採用（MVP 階段）。
  - 「不要手刻音訊底層」的建議合理，但我們的底層**已經刻好、上線、被 21+ 項
    自動化測試守護**（重連/續連/降級全都處理），沉沒成本已付清
  - LiveKit 需要 token 伺服器＋帳號＋潛在費用，破壞「純前端 BYOK、
    key 不離開裝置、零維運」的既有原則；本專案是同裝置麥克風→WS，
    沒有多方 WebRTC 需求，LiveKit 的價值（多人媒體路由）用不上
  - Next.js 需要建置管線；buildless PWA 已滿足「HTML 手機桌面 app」需求，
    且本環境 Vercel 部署通道曾不可用（GitHub Pages 路線已驗證可靠）
  - **保留給 Post-MVP**：通話口譯、會議廣播口譯（一對多）才是 LiveKit
    真正發揮的場景，屆時參考 Google 的 Broadcast Translation 範例架構
- **Supabase 帳號/雲端逐字稿**：MVP 用 IndexedDB 本機留存即可（隱私更佳），
  雲端同步列 Post-MVP

## v4 實作階段

1. **通話狀態機**：idle →（開始對話：開麥克風＋雙連線）→ in-call →（結束）→ 逐字稿檢視
   - 沿用現有 audio.js（單一 context/看門狗/track enabled 防線）與 live.js，不動底層
2. **面對面佈局**：`section.side.theirs`（rotate 180°）＋ 中控列 ＋ `section.side.mine`；
   每側：lang label＋pulse dot／最新譯文（大）／原文參考（小淡）／按住說話鈕；
   「翻譯中」跳動點固定高度區
3. **聆聽模式**：頂部模式切換（對話｜聆聽）；聆聽＝單連線、單區正向、點按切換收音、語音開關
4. **逐字稿**：IndexedDB store＋turn 寫入（放開時開 turn、譯文定稿後存）＋
   檢視面板（複製/分享/匯出/清除）
5. **視覺刷新＋無障礙**：單一強調色、outline SVG 圖示、44pt、aria、波形回饋
6. **測試**：smoke 擴充（通話開始/結束流程、雙側路由、聆聽模式、逐字稿寫入/匯出）
7. **部署驗證**：bump version → gh-pages → 線上逐檔比對
